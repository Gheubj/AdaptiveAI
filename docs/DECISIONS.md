# Decisions

## D-001 — Preserve raw sources by content hash

Imported archives are copied byte-for-byte below a SHA-256 directory and accompanied by a JSON
manifest. This makes every processed table traceable to immutable input bytes.

## D-002 — Separate historical and current pricing

`evaluations.historical_cost_usd` stores upstream request-era cost. OpenRouter snapshot prices are
stored in `model_catalog_snapshots` as USD per million tokens. They are never overwritten or used
as substitutes for each other.

## D-003 — No fuzzy model identity joins

Cross-source identity is accepted only for exact model ID or canonical-slug matches. Approximate
names may be candidates for manual review but are not merged automatically.

## D-004 — Aggregate time is not request latency

Upstream file-level `time_taken` is retained as `aggregate_file_time_seconds`.
`request_latency_seconds` remains null unless a source explicitly establishes per-request timing.

## D-005 — Split by query/duplicate group

All model responses to a query share a query ID. Exact and high-Jaccard near duplicates form one
group, and a seeded hash assigns that entire group to one split. Task types can be held out as an
OOD test split.

## D-006 — Keep upstream metric semantics

Normalized scores are named `upstream_score`; no assumption is made that accuracy, pass@1,
success rate, and judge scores are interchangeable.

## D-007 — Resumable acquisition

The official archive is downloaded into an ignored persistent `.part` file. HTTP Range resumes
after transport failure, the final tar is integrity-checked, and an existing manifest is reused
only after size, SHA-256, and tar validation all pass.

## D-008 — Conservative scalable duplicate candidates

Exact normalized text is merged directly. Near-duplicate candidates are generated by four SimHash
bands within the same task and exact numeric-token signature, with oversized blocks skipped.
Candidates still require token Jaccard >= 0.92. Numeric differences are a hard veto to prevent
merging templated but semantically different questions such as `2+2` and `2+3`.

## D-009 — Exclude ambiguous repeated pairs in preliminary baselines

Overlapping upstream subsets create repeated query/model observations and some score conflicts.
Phase 1B baselines exclude repeated pairs; Phase 2 must freeze a source-release selection rule.

## D-010 — Primary and secondary matched pools

Use the 20-model lightweight common panel as the primary quality-routing pool and the eight-model
proprietary common panel as a secondary historical-cost experiment. Sparse version IDs are excluded.

## D-011 — Mean repeated observations, with sensitivity policies

Repeated rows estimate one query/model cell and never increase the independent query count. The
primary cell is the mean of observed runs; deterministic representative and exclusion are reported.
Missing scores are never zero-imputed.

## D-012 — Success predictors rather than single-label model classification

TF-IDF fits one binary success predictor per model, allowing several models to be correct. Routing
maximizes predicted success or predicted success minus a validation-selected expected-cost penalty.

## D-013 — OOD pool compatibility is mandatory

ARC-AGI has no lightweight observations, so lightweight-20 OOD is marked infeasible. The pool is not
changed after observing this; proprietary-8 provides the only frozen matched OOD experiment.

## D-014 — Hashed trainable features before pretrained encoders

Phase 3 uses CPU-scale hashed EmbeddingBag encoders. This controls compute and avoids an unnecessary
large model download. Semantic pretrained representations remain a future budget-matched ablation.

## D-015 — Trainable gate requires a deterministic control

Architecture C learns from frozen B predictions, query state, and train costs. It is always compared
with direct `quality - lambda cost` selection using the same predictions.

## D-016 — Phase 4 entry criteria are not met

No neural architecture beats TF-IDF ID, all remain below Best Single OOD, and C fails its control.
The hardware-aware design is documented, but implementation is blocked.

## D12 — Freeze MiniLM for Phase 3.5

Use revision `c9745ed1d9f207416be6d2e6f8de32d1f16199bf`, frozen at 128 tokens. Do not evaluate BGE on the
already inspected test merely to select the more favorable encoder.

## D13 — Continue routing research

Do not enter Phase 4. Semantic methods fail to dominate TF-IDF ID and Best Single OOD. Carry only
the revised constrained gate and confidence fallback into a preregistered independent evaluation.

## D14 — Freeze routing; proceed with validation limitations

No public benchmark supports direct frozen-policy confirmation on the same exact model versions and
paid inference is prohibited. This is not an engineering blocker. Freeze the routing candidates and
proceed to real local hardware measurement while retaining exploratory labels on all generalization
claims.

## D15 — Use llama.cpp and a two-model Q4 pool

Use pinned CPU-native llama.cpp with Qwen2.5-0.5B and SmolLM2-1.7B Q4_K_M. The 1.453 GB pool fits
download/RAM constraints and gives a measured speed/memory contrast.

## D16 — Continue hardware research

Do not begin a Product MVP from an eight-query endpoint. Preserve the prototype, expand objective
quality coverage, and improve persistent model lifecycle before Phase 5.

## D17 — Freeze Local Benchmark V2 before inference

Use 500 locally authored objective tasks with fixed 150/100/250 splits and six approximately
stratified families. Preserve Phase 4 as exploratory evidence; do not pool or rescore it.

## D18 — Retain failures and task-aware scoring

Use the frozen typed scorer, record ambiguity explicitly, and keep backend timeout/crash rows in the
quality denominator. Never accept arbitrary answer containment or execute generated code.

## D19 — Proceed to an experimental MVP with research limitations

The local system and recovery paths support an experimental release, but the two-model pool has
only .008 oracle headroom over Fixed Strongest and switching removes the offline Task-Aware latency
benefit. Phase 5 must package safe local functionality without claiming routing superiority.

## D20 — One resident model with explicit hysteresis

Use one llama.cpp child, dynamic loopback ports, safe unload, and no hidden retry. Stickiness applies
only to Balanced/Hardware-Aware below a documented threshold and never overrides explicit selection
or hard constraints.

## D21 — Optional research dependencies

Keep HTTPX, Pydantic, and psutil as core. Put numerical/data/torch/encoder stacks in a research extra
and lazy imports so serving does not load benchmark infrastructure.

## D22 — Block publication pending owner controls

Do not publish until the owner approves license/attributions, destination, and exact initial commit
after secret, size, and restricted-data review.
